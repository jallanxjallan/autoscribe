# AI Watermarking, IP, and Data Retention — Recap

Reference notes from a conversation on September 9, 2026.

## 1. AI Watermarking

**What it is:** A hidden signal embedded in AI output so it can be identified as AI-generated after the fact — invisible to normal reading, detectable by a tool built to look for it.

**Two mechanisms:**
- **Text watermarking** — biases word/token choices during generation. Survives copy-paste. Light editing usually doesn't remove it; a full rewrite does.
- **File provenance metadata (C2PA)** — a signed note attached to file metadata (PNG, JPG, SVG). Doesn't change the file itself. Trivially stripped by re-saving or format conversion.

**Regulatory driver:** EU AI Act Article 50(2), effective August 2, 2026, requires generative AI providers to mark synthetic output as machine-readable, where feasible.

**Claude specifically:** Models launched on or after August 2, 2026 embed a text watermark and attach C2PA metadata to supported files, applied at the model level across all Claude surfaces (API, claude.ai, Claude Code, Cowork, Tag), worldwide, no opt-out. Anthropic's own guidance: finding a Claude mark only means Claude processed the content somewhere — it doesn't mean the underlying material isn't the user's own writing (e.g., submitted for proofreading or condensing).

## 2. Personal Style Models for Flagging

Training a model on your own writing builds a personalized baseline, not an AI detector. It flags *deviation from your usual patterns* — vocabulary, syntax, rhythm — not *origin*. A flagged phrase could be AI-inserted, editor-changed, or just an intentional register shift.

Failure modes:
- Narrow/single-genre training corpus → false positives when writing in a different register
- Thin corpus → noisy baseline, high false-positive rate

This is the mechanism behind a local span-classification model as an alternative to an LLM trope-flagging pass — same tuning problem as any native-reviewer escalation target: getting the threshold tight enough not to bury a human reviewer in noise.

## 3. IP and Ownership When Using Claude on Original Work

**Output ownership:** Anthropic's terms (consumer and commercial) assign to the user whatever rights it holds in outputs. Not a copyright guarantee on its own — purely AI-generated text with no human authorship gets thin/no copyright protection under current US law. Directing the condensing of your own original material, with editorial judgment, is a much stronger authorship claim than a bare prompt-and-accept.

**Input privacy / training (consumer plans — Free/Pro/Max):** Training flipped from opt-in to opt-out. New/resumed chats train the model by default unless "Help improve Claude" is switched off in Privacy Settings; opting in extends retention to five years.

**Commercial/API/Work accounts:** No training on customer content by default, per the Commercial Terms.

**Watermark ≠ authorship claim.** Repurposed/condensed text will carry Claude's watermark since it's freshly generated — that signals "Claude touched this," not "this isn't your original work."

Not legal advice — human-AI collaborative authorship is still unsettled copyright law. Worth a real conversation with an IP lawyer if this is central to a professional practice.

## 4. A Pipeline's Actual External Exposure (API-only architecture)

In a single multi-step run mixing RAG, local models, and an external LLM API:
- RAG retrieval (e.g. per-operator vector store) — own infrastructure, no external exposure
- Local/distilled model steps — own infrastructure, no external exposure
- External LLM API calls — the only external leg, governed by whatever commercial terms apply (typically: no training on customer content)

Nuance: "not trained on" ≠ "not retained at all" — see §6.

Uneven watermark coverage: spans generated by the external API carry that provider's mark; spans from local models don't, unless built in separately. Worth treating as a known property of the pipeline's output, not a surprise later.

## 5. Multiple LLMs Processing the Same Text

Each provider watermarks with its own private key — a second model has no visibility into the first model's bias, it just writes.

- **Light edit** by model B: the original signal (a statistical sum over many tokens) mostly survives.
- **Heavy rewrite/paraphrase** by model B: reliably breaks detection of the original mark. That span then only carries model B's fingerprint, if any.

Result: a multi-model pipeline produces a **provenance mosaic** — no single external detector can read the whole document once two or more models have touched it. Detection confidence tracks how much contiguous untouched text survives, which is invisible from outside the pipeline.

Consequence: a pipeline's own internal audit trail (e.g. a git-based audit branch plus a SQL ledger recording which engine touched which step) is the only reliable source of truth for "where did this sentence come from" — not external watermark detectors.

Caveat: watermark keys themselves aren't unbreakable — there's active research on stealing or spoofing a provider's key to misattribute unrelated text. Don't treat any watermark hit as forensic-grade proof, in either direction.

## 6. Data Retention: Correction + Forensics Standards

**Correction made mid-conversation:** an earlier claim of a blanket 7-day API retention window (sourced from a secondary blog, not verified) was wrong. Per Anthropic's own documentation: conversation content isn't retained by default for standard Messages API calls at all. Exceptions: a few features keep a bounded technical artifact briefly (e.g. cache fingerprints); flagged content can be held up to 2 years; a small set of specific models require a mandatory 30-day retention window.

**Forensics/security industry benchmarks** (general comparison, not a claim about any specific provider):
- PCI DSS: 1 year total, 3 months (90 days) immediately queryable
- NIST 800-171 / DFARS: 90-day floor for federal contractors
- General security practice: retain roughly 2x the expected breach-detection window; average time-to-detect runs close to 200 days industry-wide, which is why 1 year is a common de facto floor absent a specific regulation

Any AI provider's abuse-monitoring window, regardless of exact length, is built for catching active misuse quickly — not full forensic reconstruction months later. Different tool, different job.

## 7. TTL Design for Intermediate Pipeline Response Keys

Three distinct purposes, three different retention profiles:

| Purpose | Store | Duration | Design note |
|---|---|---|---|
| Operational debugging | Disposable runtime cache (e.g. Redis) | Hours–low days | Should match the pipeline's own failure-detection timeout/reset-count design |
| Forensic/evidentiary record | Durable audit trail (e.g. git branch + SQL ledger) | Sized to need — 90 days–1 year+ if serving this role | This is the layer that should follow security-industry benchmarks, not the disposable-cache TTL |
| Fine-tuning / process-step tuning | Separate curated store (a promoted subset, not the raw cache) | Weeks–a couple months, accumulated | Needs sampling rather than blanket retention, version-tagging to the exact instruction/engine version at capture time, and routing through whatever consent framework governs using pipeline data to improve the system |

Key point: don't solve the fine-tuning need by extending the disposable cache's TTL — that conflates a cache-lifetime decision with a curated-dataset decision, and reopens the client-data-consent question separately.
